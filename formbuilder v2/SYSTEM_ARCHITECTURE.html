Formbuilder v2 - System Architecture

Generated from current codebase inspection on 2026-04-10. Source root: src/main/java/com/sttl/formbuilder.

1) System Overview

Architecture Style

  • Spring Boot monolith with MVC + REST controllers.
  • Session-based authentication (Spring Security + HTTP session cookie).
  • PostgreSQL with mixed persistence:
    • JPA entities for metadata and access control.
    • Dynamic SQL tables for form submissions.

API Base Path

  • Configured in application.properties: api.base-path=/api/v1.
  • Primary groups: /api/v1/admin/*, /api/v1/auth/*, /api/v1/forms/*, /api/v1/publish/*, /api/v1/files/*.
  • Legacy/compatibility endpoints still available under /api/v1/admin/versions/*.

Core Transaction Flows

Flow A: Create and publish form
  1. POST /api/v1/admin/forms or /api/v1/forms creates forms row + initial form_versions(DRAFT).
  2. POST .../fields stores field definitions in form_fields.
  3. POST .../publish calls SchemaService.publishVersion().
  4. System creates/syncs dynamic table form_data_{sanitized_form_name}_{short_uuid}.
  5. Version status updated to PUBLISHED, active published version switched, old drafts cleaned.
Flow B: Public submit response
  1. GET /api/v1/publish/{formId}/published serves published definition + fields.
  2. POST /api/v1/publish/{formId}/submit validates status, schema drift, required fields, unique fields, business rules.
  3. Submission inserted into dynamic table with metadata (submitted_by, version_id, status, deleted).
  4. Response payload includes success message and submissionId.
Flow C: Approval-driven action (sub-user)
  1. User endpoint checks PermissionService and optional requiresApproval().
  2. If approval required, API creates/updates approval_requests(PENDING) and returns 202 Accepted.
  3. Admin approves/rejects via /api/v1/admin/approvals/{requestId}/approve|reject.
  4. On approve, controller executes deferred action (publish/delete/etc.) through service layer.

3) Security Architecture

Authentication

  • Spring Security uses DaoAuthenticationProvider with UserService(UserDetailsService).
  • Passwords hashed with BCryptPasswordEncoder.
  • Login endpoint authenticates using AuthenticationManager and stores SecurityContext in HTTP session.
  • Session policy: IF_REQUIRED, max concurrent sessions per user = 5.

Authorization

  • Route-level auth configured in SecurityConfig.
  • Public endpoints: auth register/login, publish endpoints, file endpoints, Swagger docs.
  • All /api/v1/** routes require authenticated session unless explicitly permitted.
  • Controller-level fine-grained checks for USER actions use PermissionService + approval flags.

CORS, CSRF, and Error Entry Points

  • CORS allows http://localhost:3000, credentials enabled.
  • CSRF disabled for REST usage with session cookies.
  • Unauthorized response: 401 JSON {"message":"Unauthorized - Please log in"}.
  • Forbidden response: 403 JSON {"message":"Forbidden - Insufficient permissions"}.

7) Request and Response Semantics

Common Successful Patterns

  • 200 OK with JSON object/list for most reads and updates.
  • 202 Accepted for actions converted into approval requests.
  • 204 No Content for module delete endpoint.
  • 200 OK binary text/csv for export endpoint.

Error Flow

  • GlobalExceptionHandler maps runtime, validation, upload, and schema drift exceptions to structured JSON.
  • SchemaDriftException -> 409 Conflict.
  • Permission-style messages -> 403, not found messages -> 404, validation/business -> 400.
  • Upload oversize -> 413 Payload Too Large.

8) Schema Drift Control and Data Integrity

  • SchemaDriftService.validateSchema() compares expected field schema vs actual DB table columns/types.
  • Startup health check marks drifted tables and blocks writes for them.
  • Submission/update paths re-check drift before accepting data.
  • Publish path blocks if current active table already drifted.

10) Notable Implementation Notes

  • Seed data currently guarantees system role Admin; no automatic seed for system role named User in current code.
  • FormController intentionally exposes dual route prefixes for compatibility.
  • Submission soft-delete behavior depends on user setting softDeleteEnabled.
  • File download endpoint contains explicit path-traversal and header-injection hardening.
